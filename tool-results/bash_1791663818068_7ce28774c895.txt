Task: Speed task close-out: end-to-end verification with the REAL small model in the browser, which exposed and fixed three real bugs the main-thread shim had masked, then final numbers and reporting.

Work Log:
- Rebuilt the stale worker bundle first (public/translator.worker.js still carried batch groupSize 8 from before the correctness decision; source said 1).
- End-to-end in-browser verification with the REAL engine (the sandbox cannot host the 600M NLLB but can host the 113 MB opus-mt q8 models): fresh visit, Set up now, real 108 MB download, initializing, warmup, ready; real translation "Good morning. The train leaves at ten past noon." -> "Bonjour. Le train part a dix heures." (Translated in 0.4 s); Details panel with real values (engine, model id, licence, device WebAssembly, per-file rows, storage 108 MB of 10348 MB, stage times, recent log, median); engine switch en->fr -> fr->en with a second real model download and correct translation; return visit auto-start to Ready after reload; Copy details graceful-failure toast under the headless clipboard block.
- Direct worker tests against the real bundle exposed that ONNX wasm inference blocks the worker's message loop: pings posted at 50 ms and 150 ms during an 883 ms inference were answered only at 894 ms. Three consequences, all real bugs the shim could not show (the shim runs on the main thread where delivery is immediate):
  1. queueMs was always 0: messages are delivered only when the previous job finishes, so "arrival" was the same moment as "start".
  2. Cancellation and priority were dead: pump() ran each delivered job synchronously inside onmessage, so sibling messages (cancels, later translates) could not be delivered before the next job started; everything ran in delivery order, stale jobs included.
  3. The heartbeat could declare a healthy worker dead: pongs cannot be delivered during inference, and a full-model batch call runs mute far past the 15 s limit.
- Fixes:
  - Worker pump: one job per pump() invocation, scheduled through setTimeout (macrotask) instead of run synchronously from onmessage; the next pick is scheduled after each job so cancels posted during a run are honoured before the next job starts; the drain-after-load hole (the old void pump() ran with loading still true, a no-op) closed via schedulePump() in the load() finally.
  - Queue wait measured on the MAIN thread: sentAt stamped per id at post time (restamped at held-queue flush, since waiting for setup is not queue backlog), computed at result arrival as arrival - sentAt - translatingMs, attached to the result message before dispatch so use-translator, Details and the speed test all read the honest number. Protocol v3 -> v4; the worker no longer posts queueMs.
  - Heartbeat: every worker message proves liveness (lastPong updated at the top of the handler); a posted translate grants a 90 s busy grace (SPEED_CONFIG.heartbeat.busyGraceMs) during which silence does not count as death; terminate clears sentAt and busyUntil.
  - use-translator: on engine error or engine switch, outstanding requests are now cancelled (engine.cancel per id) instead of just dropped from the books, so sentAt stamps and netlog in-flight marks cannot leak.
- Re-verified after the fixes with the real model in the real browser:
  - Queue waits now real: 5 simultaneous sentences waited 9/148/406/746/1045 ms, matching the serial backlog exactly.
  - Cancelled queued job never ran (posted c0,c1,c2 + cancel c1 -> results only for c0 and c2).
  - Priority honoured (posted fragment, batch, manual -> ran manual, fragment, batch).
  - App-level: pasted 4 sentences -> Details log shows waited 0.0/0.2/0.4/0.8 s; speed test reports "About 0.3 s per sentence on this device. Waiting in the queue took 0.4 s."; speed test correctly disabled with its explanation when the source is not English.
  - Typing flow, engine switch, reload return visit re-verified; lint clean; dev.log clean; zero page errors after discounting the leftover markers of my own debug observer (verified count does not grow); screenshots at 1440 and 390 reviewed by vision checks (the flagged bottom-left "N" circle is the Next.js dev-tools indicator in shadow DOM, dev-only, not app UI; a fresh screenshot without it is clean).
- Known limits restated honestly: a wasm job that already started always runs to completion (message delivery is blocked during inference; no cross-thread signal without cross-origin isolation), so stale work is bounded to the single running sentence and its result is dropped. The stopping criteria stays for any device where generation yields (WebGPU). Batch grouping stays off (groupSize 1) for the trailing-artifact reason recorded in speed-config.ts.
